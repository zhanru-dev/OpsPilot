# v1.1 Media and Webhook Runbook

This runbook covers the local/demo environment, updated for integrated multipart media. It is operational guidance, not a production incident policy. See the [media integration report](../integration/media-library-migration-report.md) for current contracts and test commands.

## Quick Triage

```powershell
npm run services:status
Invoke-RestMethod http://localhost:4100/api/v1/health/live
Invoke-RestMethod http://localhost:4100/api/v1/health/ready
```

Expected readiness dependencies are `database: up`, `objectStorage: up` and `queues: up`. Authenticated managers can inspect `/api/v1/health/metrics` for waiting, active, delayed and failed queue counts plus persisted outbox/webhook failures.

Check the API and worker terminals together. Worker records are structured JSON with an event name, entity ID and attempt information.

## Media Is Stuck in Uploading

1. Confirm MinIO is healthy with the service configuration used by this environment.
2. For multipart uploads, use **Retry / resume**; after a reload reselect the exact original file. The server discovers confirmed parts. A different content hash is rejected.
3. The original limit is100 MiB; non-final parts are5 MiB. Grant URLs expire after60s; retries request fresh authorization. Upload sessions expire after24h.
4. A lost completion response or FINALIZING state should be retried on the same session. Do not create another asset or manually mark it ready.
5. The worker reconciles unfinished expiry and durable cleanup every30s. Ready assets are no longer automatically deleted after24h. Only cancelled/expired/integrity-failed or explicitly deleted assets are cleaned.
6. Legacy single-PUT intents retain their original600s URL and completion API; new UI uploads use multipart.

Common causes:

- `403` from storage: expired or altered signed URL/headers.
- completion says object missing: the PUT did not finish.
- size mismatch: the bytes sent differ from the signed intent.
- MIME mismatch: the browser sent a different `Content-Type` header.

## Media Is Stuck in Processing

1. Confirm Redis and the worker are running.
2. Inspect `health/metrics`; `media.active > 0` means a worker owns the job.
3. Restart only the worker with `npm run dev:worker`. Startup and30s periodic recovery republish durable unfinished jobs missing from Redis. Healthy active/delayed jobs remain with BullMQ; stalled jobs recover after its lock/stall interval. Terminal queue/DB mismatches become FAILED with a visible reason.
4. If the database says `PROCESSING` but no worker is active, inspect the latest `MediaProcessingAttempt` and worker exit logs before changing state.

Temporary working directories use the OS temp folder and are removed in a `finally` block. A killed process can leave a temp directory; remove it only after confirming no FFmpeg process owns it.

### Historical trace-collision recovery

Migration `20261031010000_media_event_correlation` separates shared correlation
trace IDs from logical-event idempotency. A trace can cover queued/completed/failed
events and multiple subscribers. Event IDs, per-job phase idempotency keys, and
the unique `(domainEventId, endpointId)` pair still prevent duplicate records.

For an old job where Redis is terminal `failed` but PostgreSQL still says
`PROCESSING`, apply the migration first and pause media workers. Use the existing
environment configuration and the exact workspace and processing-job UUIDs:

```sh
node scripts/reconcile-media-processing.mjs --workspace <workspace-uuid> --job <job-uuid>
node scripts/reconcile-media-processing.mjs --workspace <workspace-uuid> --job <job-uuid> --apply
```

The first command only previews. `--apply` refuses another workspace, nonfailed
queue entries, superseded runs, completed-event evidence or changed database
state. It marks the stranded run FAILED, records its failure/audit event, and
retains source/derivative objects. Resume workers, then use the existing **Retry
processing** control. Successful retry registers its own generation-specific derivatives; terminal reconciliation removes unregistered older output objects. Never
mark an asset READY manually. Missing Redis entries require manual investigation;
the command deliberately refuses to guess. No recovery command is automatically
run against shared data.

## Media Processing Failed

Use Media Library processing details to identify the persisted failure code:

| Code prefix                     | Meaning                               | Action                                    |
| ------------------------------- | ------------------------------------- | ----------------------------------------- |
| `MEDIA_DURATION_INVALID`        | ffprobe returned no valid duration    | Verify the file is complete and playable  |
| `MEDIA_DURATION_EXCEEDED`       | Source exceeds five minutes           | Upload a bounded sample                   |
| `MEDIA_VIDEO_CODEC_UNSUPPORTED` | Video codec is outside the allow-list | Export H.264, HEVC or MPEG-4 input        |
| `MEDIA_AUDIO_CODEC_UNSUPPORTED` | Audio codec is outside the allow-list | Export AAC, MP3 or supported PCM input    |
| `FFMPEG_UNAVAILABLE`            | Worker cannot locate bundled FFmpeg   | Reinstall dependencies and restart worker |

BullMQ performs up to three attempts for transient failures. After the final attempt, a manager or content operator can use **Retry processing**, which creates a new persisted job. Successful jobs upsert variants by media, kind and profile version, preventing duplicate active derivatives.

## Webhook Is Retrying

1. Open Integration Centre and inspect the latest attempt, HTTP response and trace ID.
2. `429` and `5xx` responses are retryable; other `4xx` responses fail without automatic replay.
3. Automatic retries use exponential delays capped at 30 seconds and a maximum of five attempts.
4. Confirm the receiver validates the same raw JSON, timestamp, event ID and signing secret.

The delivery uses these correlation headers:

- `idempotency-key` and `x-opspilot-event-id`: stable domain-event ID;
- `x-opspilot-attempt`: persisted attempt number;
- `x-opspilot-trace-id`: delivery trace ID;
- `x-opspilot-timestamp` and `x-opspilot-signature`: replay and authenticity controls.

## Webhook Failed Permanently

1. Correct the receiver condition first.
2. Use **Retry delivery** as an Operations Manager or Admin.
3. Confirm Integration Centre shows a later successful attempt on the same delivery ID.
4. Do not create a duplicate endpoint as a retry mechanism.

The `(domainEventId, endpointId)` database constraint suppresses duplicate delivery records. Receivers must still persist their own idempotency decision before performing side effects.

## Outbox Backlog

If `pendingOutbox` rises while the outbox queue is idle:

1. Confirm the worker process is running.
2. Confirm Redis is healthy.
3. Restart the worker; the five-second scheduler is recreated on startup.
4. Inspect `outbox.dispatch.failed` logs and the row's `lastError`.

Outbox records retry up to ten dispatch attempts. Do not delete failed rows during diagnosis; they are the evidence that a committed domain mutation was not published.

## Dependency Recovery

```powershell
npm run services:up
npm run db:deploy
npm run dev
```

- PostgreSQL recovery restores API state and all persisted evidence.
- Redis loss removes execution state, but media startup recovery and pending outbox rows restore unfinished work.
- Object-storage loss cannot be reconstructed from PostgreSQL; restore the bucket before replaying processing.

## Safe Local Reset

For an isolated demo environment only:

```powershell
npm run db:seed
```

Seeding deletes and recreates relational demo data. It does not delete object-storage bytes or Redis jobs. Stop API/worker processes and clear only the dedicated local queue/storage resources when a fully clean demo reset is required. Never use the local reset procedure against shared or production infrastructure.


## Safe media deletion and consistency

Delete only unreferenced terminal assets. Detach from events first; processing or
unfinished uploads return409 (use upload cancellation for unfinished transfers).
Deletion commits a tombstone plus cleanup intent before external object removal.
A storage outage or failed database cleanup commit leaves retryable evidence.
Cleanup waits for upload grants to expire and operates only on the asset's exact
owned prefix. Never delete a shared bucket to repair one asset.

If a preview object is missing, URL issuance fails and reconciliation marks the
asset FAILED. Restore storage or retry processing when the original survives.
API/worker SIGKILL recovery preserves asset/job identity; killed processes may
leave OS temp directories. Inspect ownership before removing abandoned
`opspilot-upload-*` or `opspilot-media-*` paths. Do not sweep active work.
